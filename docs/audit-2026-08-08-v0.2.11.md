## 第一部分：内存与性能专项分析

用户反馈"当前内存占用极高"。下面先给出量化归因，再给出按性价比排序的优化方案。

### 归因：内存去了哪里

默认 `maxLiveFrames: 3`（`src/core/defaults.ts:14`），加上 1 个列表 iframe，宿主页常态持有 **4 个同源 iframe**。每个 iframe 都是一个完整的 Discourse 单页应用实例，各自持有独立的 Ember 运行时、路由、组件树、`MessageBus` 长轮询连接与图片解码缓存。

**这是占用的绝对主体，且是架构的固有成本，不是泄漏。** 我逐一排查了常见泄漏模式，均未发现问题：

- `renderTabStrip` 使用 `root.ondragstart =` 属性赋值而非 `addEventListener`（`src/tabs/tab-strip.ts:209-267`），重复渲染不会叠加监听器
- 标签节点按 `data-tab-id` 复用（`src/tabs/tab-strip.ts:268-288`），不整栏销毁重建
- 渲染状态存于 `WeakMap`（`src/tabs/tab-strip.ts:52`）
- 预览缓存有条目数与字节数双重上限（`src/preview/preview-controller.ts:602-606`）
- 定时器与观察器在 `destroy()`/`remove()` 路径中均有清理

所以**优化方向不应是"找泄漏"，而应是"降低每个 iframe 的常驻成本"**。

### 关键发现 A：每个 iframe 都完整解析了整个 322 KB 脚本（代码确证）

`@run-at document-start` + 无 `@noframes`（`src/meta.ts:10-16`），因此 Tampermonkey 会把**完整的 322 KB 打包产物**注入到每一个同源 iframe。而 iframe 侧真正需要的只有 `bootFrameBridge` 及其三个依赖：

```
src/frame-bridge.ts:1-3
  ensureEmbeddedStyles  (src/ui/styles.ts)
  getTopicInfo, isSupportedTopicTarget  (src/discourse/routes.ts)
  readTopicCategory, readTopicDocumentCategory  (src/discourse/category.ts)
```

即在 4 个 iframe 中，以下内容被解析、编译、并常驻为堆对象，却永远不会执行：

| 模块 | 源码体积 | iframe 内是否需要 |
| --- | --- | --- |
| `link-hover-previewer-upstream.ts` | 142,867 B | 否（`installLinkHoverPreviewer` 仅由宿主侧 `upstream-preview-controller.ts:23` 调用） |
| `APP_STYLES` 字符串常量 | 26,390 B | 否（iframe 用的是 3,730 B 的 `EMBEDDED_STYLES`） |
| `app.ts` | 38,933 B | 否（`startLinuxDoApp` 在 `window.self !== window.top` 时不执行） |
| `preview-controller.ts` + `sanitizer.ts` | 27,177 B | 否（且宿主侧也不可达，见 P1-3） |
| `settings-panel.ts` / `credit-widget.ts` / `layout-controller.ts` / `tab-strip.ts` | 约 53,000 B | 否 |

**这是本次审计中性价比最高的优化点。** `EMBEDDED_STYLES` 只有 3,730 B，即 iframe 侧携带了约 26 KB 完全无用的 CSS 字符串常量 —— 0.2.7 已经把样式拆成两份载荷，但**拆分只作用于注入哪一份，两份字符串仍然都在每个 frame 的堆里**。

### 关键发现 B：软冻结未触及 iframe 内真正的开销源（代码确证）

0.2.8 的软冻结（`src/frame-bridge.ts:122-148`）暂停的是：本脚本自己的 `metadataObserver`、自己的延迟发送定时器、媒体元素与 Web Animations。

它**没有**暂停 iframe 内 Discourse 本身的活动：Ember 的 `runloop`、`MessageBus` 长轮询、以及 Discourse 自己的后台节能分支。原因是脚本从未向被隐藏的 iframe 传达"你不可见"这一信号 —— 我已确认 `src/` 中除 `credit-widget.ts` 读取自身可见性外，**没有任何 Page Visibility 相关处理**，且 iframe 上未设置任何 `loading` / `sandbox` / `fetchPriority` 属性。

结果是：3 个隐藏的帖子 iframe 各自维持着 `document.visibilityState === "visible"`，Discourse 认为它们在前台，继续跑 runloop、继续长轮询、继续处理已读上报。

**项目里已经有现成的正确答案。** 上游预览核心自带一个 `createPageVisibilityController`（`src/preview/link-hover-previewer-upstream.ts:63-130`），其设计注释恰好描述了我们需要的语义：

> 以标准 Page Visibility 语义暂停被遮挡的页面。这里不冻结 JavaScript，也不改写定时器；只让 Discourse 等 SPA 主动进入它们原生的后台节能分支。

即：在被隐藏的 iframe 内，把 `document.hidden` 覆写为 `true`、`visibilityState` 覆写为 `"hidden"` 并派发 `visibilitychange`，让 Discourse **主动走它自己的后台分支**。这符合项目原则中"预览核心保持上游实现"（我们不修改它，只是在 frame-bridge 侧采用同一技术），也符合"不靠强制刷新降内存"。

### 性能优化方案（按性价比排序）

#### 优化 1：iframe 侧不再携带宿主侧代码（收益最高）

**做法** 在 `scripts/build.ts` 中产出两个入口并合并为一个产物：顶层执行 `startLinuxDoApp`，frame 侧执行 `bootFrameBridge`，通过一个轻量的运行时判断选择，但让 esbuild 能对两条路径分别做 tree-shaking。最简可行方案是把 frame 侧依赖收敛为独立入口，宿主侧代码用动态 `import()` 或在构建期生成两段 IIFE 并以 `window.self !== window.top` 包裹，使 frame 分支的字面量与函数体不进入同一作用域。

**预期收益** 每个 iframe 少解析约 250 KB 源码。以常态 4 个 iframe 计，可显著降低 JS 堆与编译缓存占用，并缩短每个 iframe 的启动时间（`document-start` 注入直接位于关键路径上）。

**成本** 中（需改构建脚本，属唯一需要动 `scripts/build.ts` 的项）。**回归风险** 中 —— 必须验证 frame 侧全部消息通道、预览转发、分类解析仍工作。**证据等级** 代码确证。

**必须保持不变的行为** frame 侧全部消息类型与载荷格式；`@run-at document-start`；预览核心一行不改；宿主侧功能完全不变。

**验证** 单测：断言 frame 入口的依赖闭包不含 `app.ts` / 预览核心 / `APP_STYLES`。真实浏览器：开 3 个帖子 + 列表，用 DevTools Memory 面板对比优化前后的 JS 堆快照；确认标签切换、预览、分类上色、书签均正常。**独立发布。**

#### 优化 2：向隐藏 iframe 传达"不可见"，让 Discourse 自行节能（收益高）

**做法** 扩展现有的 `ldu:frame-lifecycle` 消息通路（`src/tabs/frame-pool.ts:260-265` 已经在发送 `active: false`，`src/frame-bridge.ts:207-210` 已经在接收）。在 `setSoftFrozen(true)` 中额外覆写该 iframe 内的 `document.hidden` / `visibilityState` 并派发 `visibilitychange`；`setSoftFrozen(false)` 时还原为浏览器真实状态。技术实现照搬上游 `createPageVisibilityController` 的模式（保存原始描述符、还原时恢复），不要自行发明。

**预期收益** 隐藏的 3 个 iframe 内 Ember runloop 与 `MessageBus` 长轮询进入后台节能状态，减少常驻 CPU 唤醒与无效网络请求 —— 这同时命中用户提到的"无效请求"与"渲染开销"。

**成本** 中低（消息通道已存在，只需扩展 frame 侧处理）。**回归风险** 中 —— 覆写 document 属性需谨慎还原，若还原不彻底会导致"切回标签后页面以为自己仍在后台"，表现为不刷新、不上报已读。这是**高风险高收益**改动，必须独立发布。**证据等级** 代码确证（机制）+ 待验证（Discourse 实际节能幅度）。

**必须保持不变的行为** 切回标签后 iframe 必须恢复真实可见状态并继续正常工作；不得依赖强制刷新；软冻结与硬挂起的分层关系不变；浏览器标签整体隐藏/显示时，未被软冻结的 iframe 仍应反映浏览器真实状态。

**验证** 单测：断言冻结时派发了 `visibilitychange` 且 `visibilityState` 为 `"hidden"`，解冻后恢复原值与原描述符。真实浏览器：开 4 个帖子静置 10 分钟，用 Network 面板确认隐藏 iframe 的长轮询请求减少；切回每个标签确认内容仍实时更新、已读上报正常。

#### 优化 3：删除不可达的预览实现与无效 CSS（收益中，成本最低）

见 P1-3。`preview-controller.ts` + `sanitizer.ts` 共 860 行不可达（已验证 esbuild 已摇除，`prepareCompatiblePreviewHtml` 在 dist 中出现 0 次，故**不影响体积**），但 `src/ui/styles.ts:466` 起约 24 个 `.ldu-preview-*` 规则**确实打进了 dist 且完全无效** —— 已验证线上生效的上游核心使用 `agy-*` 前缀类名（`ldu-preview` 在上游文件中出现 0 次）。删除这些 CSS 可直接缩减 `APP_STYLES`，与优化 1 叠加时收益进一步放大。

#### 优化 4：给 iframe 加载加上浏览器级提示（收益低，成本极低）

`prepare()` 创建的后台帧目前未设置任何加载提示。可为**非活动**帧设置 `loading="lazy"`。注意这只影响首次加载调度，对已加载帧无效，因此收益有限。**不要**用 `fetchPriority` 做永久降级 —— 0.2.11 的变更说明已明确否决了"永久低请求优先级"这一方向，此处应保持一致。

## 第二部分：缺陷清单

### P0-1 手动拖拽的标签顺序会被静默丢弃（实测）

**实测输出**

```
拖拽后            : 3,1,2
打开第 4 个帖子后 : 1,2,3,4     ← 顺序被重排
刷新恢复后        : 1,2,3       ← 顺序被重排
```

**根因** `tabs` 数组同时承担"显示顺序"与"最近活跃排序"两个语义：

- `src/core/session.ts:125-127`：`upsertTopicTab` 每次 `open` 都 `.sort((a,b) => a.lastActiveAt - b.lastActiveAt)`
- `src/core/session.ts:73-75`：`normalizeSession` 加载时同样重排
- `src/tabs/tab-store.ts:144-167`：`reorderInPane` 只改数组位置，**不写任何 `lastActiveAt`**，手动顺序因此没有任何持久化载体

**严重程度** 中高。**发生概率** 高（任何拖过标签的用户，接着开一个新帖子或刷新一次即触发）。**用户影响** 排好的顺序无征兆跳回原样，用户会认为 0.2.2 的主打功能坏了。**触发条件** 拖拽 → 打开新帖子（或刷新）。

**修复收益** 高。**实施成本** 低。**回归风险** 中（排序语义被 `upsertTopicTab`、`normalizeSession`、`closeTopicTab`、`repairPanelOwnership` 共用）。

**推荐修复思路** 不要用 `lastActiveAt` 编码顺序 —— 那会污染帧池的 LRU 淘汰依据（`frame-pool.ts:300`）。推荐：**`tabs` 数组本身即权威顺序**，移除 `upsertTopicTab` 与 `normalizeSession` 中的 `.sort`，仅在超出 `MAX_TABS` 需淘汰时才按 `lastActiveAt` 挑选被淘汰者。备选方案是新增 `tabOrder: string[]` 字段，但改动面更大。

**必须保持不变的行为** 新帖子仍追加到末尾并成为活动标签；超过 `maxOpenTabs`(50) 时仍淘汰最久未活跃且非活动的标签；`secondaryTabIds` 分区归属与双区激活态不变；同 `topicId` 重复打开仍复用原标签。

**需要补充的测试** 单测：拖拽后 `open` 新帖子顺序不变；拖拽 → 序列化 → `normalizeSession` 顺序不变；拖拽后触发 `MAX_TABS` 淘汰，剩余相对顺序不变；双阅读区各自独立排序互不影响。真实浏览器：拖三个标签换序 → 从列表开第四个 → 确认顺序 → F5 → 再确认。

**漏检原因** `tests/tab-store.test.ts:67-79` 只在孤立状态下测 `reorderInPane`，从不在其后接 `open` 或 `normalizeSession`。

**独立发布** 是。

### P0-2 硬挂起把已保存的滚动位置覆盖为 0（实测）

**实测输出**

```
挂起前存储 : 4200
挂起后存储 : 0        ← 4200 才是正确值
```

**根因** `src/tabs/frame-pool.ts:296-311` 的 `suspendOverflow` **先移除 iframe（:307 `record.iframe.remove()`）再回调 `onSuspend`（:310）**；而 `src/app.ts:436-439` 与 `:456-459` 的回调体是 `const scrollY = iframe.contentWindow?.scrollY ?? 0`。iframe 已脱离文档，真实浏览器下 `contentWindow` 为 `null`，取到 `0` 并写回 store。

**关于 jsdom 的重要提示** jsdom 在 `remove()` 后仍保留 `contentWindow`，这正是 `tests/frame-pool.test.ts:45-55` 能通过、并且把这一错误顺序**断言成期望行为**（`connected: false`）的原因。"移除后 `contentWindow` 为 null"是标准浏览器行为、可信度高，但**未在真实浏览器实测**，修复时请以浏览器验证为准。

**严重程度** 中高。**发生概率** 中高（默认 `maxLiveFrames: 3`，开到第 4 个帖子即触发一次淘汰）。**用户影响** 被淘汰的标签回来时从头开始，深读位置丢失；整套滚动恢复机制（`restoreScroll`、`restoreDeadline`、收敛重试）恰在最需要它的场景下失效。

**修复收益** 高。**实施成本** 低（数行）。**回归风险** 低。

**推荐修复思路** 在 `suspendOverflow` 内于 `remove()` **之前**读取 `record.iframe.contentWindow?.scrollY`，作为参数传给 `onSuspend`；`app.ts` 两处回调改用该参数。同时把 `onSuspend` 签名从 `(tabId, iframe)` 收窄为 `(tabId, scrollY)`，从类型上杜绝再次误读已卸载的 iframe。

**必须保持不变的行为** 淘汰仍选最久未使用且非当前活动的帧；仍写入 `suspended: true`；仍触发 `schedulePersist`；`activeTabId` 命中时的清空逻辑不变；软冻结与硬挂起的分层关系不变。

**需要补充的测试** 单测：`liveLimit=1`，给活动帧非零滚动位置，触发溢出，断言 store 中 `scrollY` 保留原值；并修正 `tests/frame-pool.test.ts:45-55` 改为断言"回调收到移除前的滚动值"。真实浏览器：`maxLiveFrames` 设为 2，A 帖滚到中段 → 开 B、C 使 A 被淘汰 → 切回 A 确认停在中段。

**独立发布** 是（与 P0-1 分开，根因与验证路径均不同）。

### P1-1 挂载重试耗尽后永久卡死（代码确证）

`src/app.ts:326-333` 的 `scheduleRouteMountRetry` 上限 30 次 × 100ms = 3 秒，而 `routeRetryAttempts` **只在挂载成功后（`app.ts:258`）才归零**。若 Discourse 冷启动超过 3 秒才产出 `#main-outlet`，此后每次 `syncRoute` 都在 `attempts >= 30` 处直接 return，分屏再也不会挂载，而 `tabStore` 中标签仍存在 —— 用户看到已打开的帖子全部消失，只能靠刷新恢复。

严重程度中，概率低（慢网络/冷启动）。成本极低：由外部事件（`popstate`、`hashchange`、MutationObserver 检测到 URL 变化）触发的 `scheduleRouteSync` 应重置 `routeRetryAttempts`。回归风险低，但**必须保留上限本身**，避免在真正无 `#main-outlet` 的页面上无限轮询。测试：单测模拟前 30 次 `mount()` 失败、随后成功，断言最终完成挂载。可与其他小修同批发布。

### P1-2 SPA 内部跳转到帖子时不会进入阅读区（待验证）

"所有帖子进入阅读区"这条要求的唯一实质缺口。六条入口路径均已核查正确：宿主页点击、列表 iframe 点击、帖子 iframe 内点击、直接访问、直接访问后的提升（`promoteDirectTopicNavigation`）、Ctrl/中键（有意放行到浏览器新标签）。

缺口在**不经过 `<a>` 点击的 SPA 路由跳转**（键盘快捷键 `j/k` + Enter、发帖后跳转等）：`location.href` 变为 `/t/...`，`syncRoute` 因 `tabs.length > 0` 判定 `shouldHostSplit` 为真（`app.ts:249-251`），分屏保持、宿主 `#main-outlet` 被 CSS 隐藏，而该帖子**没有**被收进标签 —— 用户按了键，界面上什么都没发生。

严重程度中，概率低到中（取决于键盘流用户比例）。**实施前必须先在真实浏览器确认 linux.do 当前快捷键是否真的绕过 `<a>`。** 若确认，修复思路：`syncRoute` 中当 `route === "topic"` 且分屏已激活且有标签时，复用现成的 `openTopic` 收编该 `topicId`。**必须避免与 `promoteDirectTopicNavigation` 及 `history` 状态形成回环 —— 这正是 v0.3 翻车的区域**，务必小步且独立发布。

### P2 级（可做，收益有限）

**P2-1 `frame-ready` 时把 store 的 `scrollY` 临时写成 0。** `app.ts:626-640`：patch 带 `scrollY: message.scrollY`（新载入帧为 0）写入 store，随后 `:638` 用**更新前的快照** `tab.scrollY` 去滚动 iframe —— 滚动本身正确，但 store 短暂持有 0，后续 scroll 事件或 `captureLiveFrameState` 会自愈。无稳定用户影响。建议：`frame-ready` 不参与 `scrollY` 写入。

**P2-2 `--ldu-header-height: 52px` 硬编码**（`styles.ts:9`）。`artifacts/audit/split-header-misalignment*.png` 说明此处历史上出过问题。论坛改版或出现公告横幅即错位。建议挂载时测一次 `.d-header` 实际高度写入变量，`resize` 时复用现有 `apply()` 通路。**属视觉回归高风险区**，需三档宽度截图对比后独立发布。

**P2-3 LDC 组件依赖 `.d-header-icons > .language-switcher` 单点。** `credit-widget.ts:62-64`：找不到该元素则 `ensureHost` 直接 return，组件永不挂载也永不请求，静默消失。加兜底宿主（如 `.d-header-icons` 末尾）即可。

**P2-4 分类色硬编码映射的兼容风险。** `tab-strip.ts:15-33` 写死 17 个分类名与 rgb 值，`resolveTabCategoryColor` 依赖解析 `document.title` 与 `/\s+-\s+LINUX DO/i` 后缀。这是 0.2.7 为避免扫描侧栏的**有意权衡**，主路径仍是元数据（`og:article:section:color`），映射只是回退。**不建议改为动态扫描**（会退回已优化掉的开销）。仅记录为已知兼容风险。

**P2-5 跨访问恢复存在无效分支。** `storage.ts:254-270` 的 `loadLatestSession` 领取最近关闭的一份后立即 `clearRestorableSessions` 清空**全部**快照，使 `MAX_RESTORABLE_SESSIONS = 8`（`storage.ts:146`）永远用不上。行为符合 CHANGELOG 0.2.1 的"只领取最后关闭的一份"，且 `restoreSession` 默认关闭，无用户影响。**收益低，建议不做。**

## 第三部分：明确建议不做

**不要为"内存增长"做防御性改造。** 未发现监听器重复绑定、观察器堆积或缓存无界增长（依据见第一部分归因）。占用主体是按设计保留的活动 iframe，受 `maxLiveFrames` 约束。在此之上再加机制只会引入复杂度，且与"不靠限制标签数或强制刷新降内存"的原则冲突。**正确的降占用路径是第一部分的优化 1 与优化 2。**

**不要修宿主 URL 与列表 iframe URL 的分离。** `navigateList` 只改 iframe 不改 `location`，导致浏览器前进/后退对应用内导航无效、地址栏与实际浏览页不符。这是 v0.2 架构的固有特征，刷新恢复已由 `session.listUrl` 解决。要改就得引入 `pushState` 管理 —— 正是 v0.3 翻车之处。**接受为已知权衡。**

**不要动上游预览核心。** 符合既定原则，0.2.3 已加哈希校验防偏离。P1-3 只删除项目自己那套未使用的替代实现；优化 2 只是**借用**其 Page Visibility 技术到 frame-bridge，不修改该文件。

**不要清理 `settings.enabled` 的死条件。** `defaults.ts:41` 强制其为 `true`，导致 `app.ts` 中约十处 `settings.enabled &&` 恒真。清理是纯风格改动，无行为收益，且会扩大 diff 掩盖真实修复。

**`maxOpenTabs` 无 UI 不是缺陷。** 它是内部上限（`defaults.ts:15`，50）且被真实使用（`app.ts:117`），仅缺文档。补一行文档即可，不必加控件。

**不要为重复逻辑单独发版。** 第一部分列出的四类重复不影响运行时占用，只影响可维护性；顺手合并即可。
